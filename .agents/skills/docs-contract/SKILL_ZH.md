# 文档与契约

> 严格中文翻译，与 SKILL.md 同步更新。

在编写文档、修改已承诺的行为，或检查文档是否与代码一致时，使用本 skill。

## 选对页面

| 内容 | 位置 |
| --- | --- |
| 外部承诺 | `docs/contract.md` |
| 分层、归属、数据流 | `docs/architecture.md` |
| 阶段计划、退出条件 | `docs/roadmap.md` |
| 带取舍的选择 | `docs/decisions/NNNN-*.md` |
| 如何执行重复任务 | `.agents/skills/<id>/SKILL.md` |
| 面向 agent 的项目规则 | `AGENTS.md` |

不要为一段本该属于上述页面之一的内容新建页面。

## 写一条契约承诺

1. 从客户端视角，用现在时描述行为。
2. 写明确切的端点、事件、字段或错误码。
3. 在能力表或相关表格中加一行。
4. 在 `Locked by` 中填入真实的测试路径。
5. 如果还没有测试，写 `pending: <phase>`，并且不要在其他任何地方把该行为描述为稳定。
6. 如果代码已存在，在同一次改动中补上测试。

没有测试的承诺就是文档里的 bug。

## 文风

- 一句话一个断言。避免“应该”“将会”“可能”。
- 术语首次出现时定义；不要依赖参考项目的词汇。
- 枚举（事件、错误码、能力）优先用表格。
- 每个消息族给一个具体 JSON 示例，不要每个字段都给。
- 中文文档保持中文。代码标识符、事件名和错误码保持英文。
- 不要文字截图。不要生成式 API 转储。

## 审查清单

- [ ] 每个“必须”都能对应到代码或测试。
- [ ] `contract.md` 中没有路线图式的措辞。
- [ ] 契约中没有 provider 名称或 provider 原始字段。
- [ ] 链接可解析；锚点与标题一致。
- [ ] `docs/README.md` 仍指向正确的入口页面。
- [ ] 如果行为变了，契约在同一次提交中一起变。
- [ ] 如果新增了能力，`GET /api/health` 与表格一致。

## 什么时候加文档站

不要加。在 `docs/` 超过约 20 页，或版本化、i18n 发布成为真实需求之前，
Markdown 加契约测试成本更低，也更不容易漂移。只有出现明确的外部受众时才重新考虑。
